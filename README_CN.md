# DJI O4 DroneID CRYP 与 INFP 规范

[English](README.md)

射频波形、信道序列与被动解调：[`RF_PHY_CN.md`](RF_PHY_CN.md)

## 范围

本文档规定 DJI O4 DroneID 的 `CRYP`、`INFP-10` 和 `INFP-11` 格式，涵盖报文封装、核心记录、密码处理、会话关联、解密后的载荷布局及验证规则。

`CRYP` 使用 SM2 公钥加密建立一个 128 位 AES 会话密钥。该会话密钥既用于解密 `CRYP` 记录携带的辅助载荷，也用于解密与其关联的 `INFP` 记录。记录通过一个 4 字节密钥标识符与正确的会话关联。

本规范以报文分析结果和本仓库中的参考实现为依据。

## 使用已知会话密钥进行验证

参考实现可以接受一个已解封的 16 字节 AES 会话密钥作为外部输入。它会检查 `key_id = SHA-256(K)[0:4]`，解密 CRYP 辅助密文及相关 INFP 密文，并验证其明文结构。此模式既不查找 `K`，也不执行 `K` 的解封。

仅提供外部 `K` 不足以验证所捕获 CRYP 中的 `C3`，因为该计算还需要 SM2 共享点 `(x2, y2)`。实现将此项检查报告为 `notChecked`。INFP 载荷解密和结构验证直接使用 `K`。

构造 CRYP 报文不需要接收方私钥：发送方使用 `Q`；只有接收方在解封并验证传输的会话密钥时才需要 `d`。

兼容的接收方公钥材料未包含在本文中。该材料可从受支持设备的固件中提取，并通过 `--public-key-file` 提供。文件格式、命令行用法及往返示例见 `EXAMPLE.md`。

## 接收方私钥保管

与 `Q` 对应的 SM2 接收方私钥由 DJI AeroScope 升级模块（型号 EA500）保管。该设备是一种硬件支持的 USB 密码模块，具有固定站版和移动版两种外形；两者的物理结构不同，但执行相同的密码功能。

AeroScope 主机与升级模块先进行多阶段认证，再建立一个独立的加密传输会话。主机将 CRYP 记录原样发送给模块。模块解封并返回 16 字节会话密钥 `K`；长期接收方私钥 `d` 始终保留在模块内部。

主机与模块之间的命令协议已经还原，但不予公布。

## 约定

- 偏移量从零开始，以字节为单位。
- 除非字段另有说明，多字节整数均采用小端序。
- 椭圆曲线坐标和标量均为无符号大端整数。
- `||` 表示字节串连接。
- `XOR` 表示对等长字节串逐字节异或。
- `0x00 × n` 表示 `n` 个零字节。
- 除非字段规定了更严格的字符集，文本均采用 UTF-8。
- `K` 是 16 字节 AES 会话密钥。
- `d` 是接收方的 SM2 私有标量。
- `Q = dG` 是接收方的 SM2 公钥点。
- `k` 是发送方新生成的 SM2 临时标量。
- `C1`、`C2` 和 `C3` 是经 SM2 加密的会话密钥的三个组成部分。

## 协议概述

发送方为一个会话创建一条 `CRYP` 记录，并发送一条或多条承载该会话数据的 `INFP` 记录。同一会话中的所有记录都携带相同的 4 字节 `key_id`。

发送方的高层流程如下：

1. 生成一个 16 字节 AES 会话密钥 `K`。
2. 使用 SM2 为接收方加密 `K`，得到 `C1`、`C2` 和 `C3`。
3. 设置 `key_id = SHA-256(K)[0:4]`。
4. 使用 `K` 和 AES-128-CTR 加密 32 字节 CRYP 辅助明文。
5. 使用 `K` 和每条记录各自的 IV，以 AES-128-CTR 加密每条 INFP 明文。

接收方的流程如下：

1. 解析并验证一条 `CRYP` 核心记录。
2. 使用私有标量 `d`，根据 `C1`、`C2` 和 `C3` 解封并验证 `K`。
3. 确认 `SHA-256(K)[0:4]` 等于记录中的 `key_id`。
4. 将 `K` 与 `key_id` 关联。
5. 解密 CRYP 辅助密文以及携带相同 `key_id` 的每条 INFP 记录。

记录的到达顺序不受限制。INFP 记录可以缓存至对应的 CRYP 记录到达，也可以在后续轮次中处理。

## 报文封装

CRYP 和 INFP 核心记录可以直接出现，也可以位于以下两种封装之一中。封装处理完成后，应向解析器提供一条核心记录。

### 直接核心记录

直接记录以下列选择符之一开头，并且必须具有表中所列的精确长度：

| 选择符 | 偏移 1–4 处的魔数 | 核心类型 | 长度 |
| ---: | --- | --- | ---: |
| `0x10` | `INFP` | INFP-10 | 128 |
| `0x11` | `INFP` | INFP-11 | 160 |
| `0x13` | `CRYP` | CRYP | 163 |

### 逻辑对象封装

逻辑对象封装的布局如下：

| 偏移 | 大小 | 字段 | 编码 |
| ---: | ---: | --- | --- |
| 0 | 1 | `payload_length` | 无符号字节 |
| 1 | `payload_length` | 载荷 | 核心记录，后面可以带有传输填充 |
| `1 + payload_length` | 2 | `crc16` | 小端序 |

封装总长度为 `payload_length + 3`。载荷以一条完整的 CRYP 或 INFP 核心记录开头。部分记录会在核心记录之后附加 7 个零字节。解析器应使用选择符确定的核心长度，并将其余载荷字节视为传输填充。CRC 覆盖长度字节和完整载荷，但不覆盖末尾存储 CRC 的两个字节。

### V1 传输封装

V1 传输封装的布局如下：

| 偏移 | 大小 | 字段 | 编码或要求 |
| ---: | ---: | --- | --- |
| 0 | 1 | 起始标记 | 必须为 `0x55` |
| 1 | 1 | 声明长度低字节 | 无符号 |
| 2 | 1 | 长度及传输标志 | 位 0–1 为声明长度的位 8–9 |
| 3 | 1 | 头部 CRC | 对偏移 0–2 计算 CRC-8 |
| 4 | 5 | 传输元数据 | 由传输层原样保留 |
| 9 | 2 | 服务标识符 | 必须为 `03 da` |
| 11 | 可变 | 服务载荷 | 核心记录，后面可以带有传输扩展 |
| 最后 2 字节 | 2 | 帧 CRC | CRC-16，小端序 |

声明的总长度为：

```text
declared_length = byte[1] | ((byte[2] & 0x03) << 8)
```

该值必须等于完整帧长度。帧 CRC 覆盖除末尾存储 CRC 的两个字节之外的所有字节。

### CRC 算法

CRC-8 的初始值为 `0x77`，反射多项式为 `0x8c`，且不执行最终异或：

```text
crc = 0x77
for byte in input:
    crc = crc XOR byte
    repeat 8 times:
        crc = (crc >> 1) XOR 0x8c  if (crc & 1) != 0
              crc >> 1             otherwise
return crc & 0xff
```

CRC-16 的初始值为 `0x3692`，反射多项式为 `0x8408`，且不执行最终异或。结果以小端序存储：

```text
crc = 0x3692
for byte in input:
    crc = crc XOR byte
    repeat 8 times:
        crc = (crc >> 1) XOR 0x8408  if (crc & 1) != 0
              crc >> 1               otherwise
return crc & 0xffff
```

## 密码参数

### SM2 曲线

协议采用素域 `Fp` 上的标准 256 位 SM2 曲线：

```text
p  = FFFFFFFEFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF00000000FFFFFFFFFFFFFFFF
a  = FFFFFFFEFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF00000000FFFFFFFFFFFFFFFC
b  = 28E9FA9E9D9F5E344D5A9E4BCF6509A7F39789F515AB8F92DDBCBD414D940E93
n  = FFFFFFFEFFFFFFFFFFFFFFFFFFFFFFFF7203DF6B21C6052B53BBF40939D54123
Gx = 32C4AE2C1F1981195F9904466A39C9948FE30BBFF2660BE1715A4589334C74C7
Gy = BC3736A2F4F6779C59BDCEE36B692153D0A9877CC62A474002DF32E52139F0A0
```

接收方公钥点 `Q` 属于可从受支持设备固件中提取的公开材料，本文不予附带。

点采用仿射坐标。`C1` 的线路编码为 32 字节大端 X 坐标，后接 32 字节大端 Y 坐标。不包含 SEC1 非压缩点前缀 `0x04`。

### SM2 会话密钥加密

为传输会话密钥 `K`，发送方执行：

```text
choose fresh k such that 1 <= k < n
C1 = kG
S  = kQ = (x2, y2)
t  = SM3(x2 || y2 || 00000001)[0:16]
C2 = K XOR t
C3 = SM3(x2 || K || y2)
key_id = SHA-256(K)[0:4]
```

`x2` 和 `y2` 均编码为恰好 32 字节的大端值。`00000001` 是值为 1 的 4 字节大端 KDF 计数器。所得 `t` 为 32 字节 SM3 摘要的前 16 字节。如果 `t` 全为零，发送方必须使用新的 `k` 重新执行 SM2 加密操作。

接收方执行：

```text
decode C1 as point (x1, y1)
validate C1
S  = dC1 = (x2, y2)
t  = SM3(x2 || y2 || 00000001)[0:16]
K  = C2 XOR t
require SM3(x2 || K || y2) == C3
require SHA-256(K)[0:4] == key_id
```

接收方必须拒绝不满足以下任一条件的 `C1`：两个坐标都位于 `[0, p - 1]`；该点满足 SM2 曲线方程；与 `d` 相乘后不产生无穷远点。摘要比较必须以常数时间完成。

### AES-CTR 载荷加密

CRYP 辅助数据和 INFP 明文使用 CTR 模式的 AES-128。每条核心记录提供一个 8 字节 `iv`。按下式构造 16 字节初始计数器：

```text
initial_counter = iv || (0x00 × 8)
```

加密和解密使用相同的 CTR 变换，不使用填充。初始计数器被解释为一个 128 位大端整数，后续每个分组将其加一。

AES-CTR 不对密文进行认证。`C3` 认证的是所传输的会话密钥，而不是 CRYP 辅助密文或 INFP 密文。封装 CRC 可以检测传输错误，但不提供密码学认证。记录认证需要另行采用认证机制。

## 会话关联

每条 CRYP 和 INFP 核心记录都包含一个 4 字节 `key_id`，其值为：

```text
key_id = SHA-256(K)[0:4]
```

在该值和 `C3` 均验证通过之前，接收方不得接受从 CRYP 获得的密钥。INFP 记录只能使用与其 4 字节 `key_id` 完全匹配且已经过认证的会话密钥解密。

该标识符是截断的密钥摘要，不能替代 `C3` 完整性检查。标识符可能发生碰撞，不得假定其全局唯一。

## CRYP 核心记录

CRYP 核心记录的长度恰好为 163 字节：

| 偏移 | 大小 | 字段 | 编码或值 |
| ---: | ---: | --- | --- |
| 0 | 1 | 选择符 | `0x13` |
| 1 | 4 | 魔数 | ASCII `CRYP` |
| 5 | 4 | `key_id` | `SHA-256(K)` 的前 4 字节 |
| 9 | 32 | `C1.x` | 无符号大端序 |
| 41 | 32 | `C1.y` | 无符号大端序 |
| 73 | 32 | `C3` | SM3 认证摘要 |
| 105 | 16 | `C2` | 掩码处理后的 AES 会话密钥 |
| 121 | 8 | `iv` | AES-CTR IV 前缀 |
| 129 | 2 | 密文长度 | 小端序 `0x0020` |
| 131 | 32 | 辅助密文 | AES-128-CTR 加密 |

线路顺序为 `C1 || C3 || C2`，而不是书写 SM2 密文时常用的 `C1 || C2 || C3` 顺序。

### CRYP 辅助明文

使用 `K` 和 CRYP IV 解密偏移 131–162。所得明文的长度恰好为 32 字节：

| 偏移 | 大小 | 字段 | 编码及比例 |
| ---: | ---: | --- | --- |
| 0 | 16 | 航空器标识符 | 以 NUL 终止或以 NUL 填充的 ASCII |
| 16 | 4 | 航空器经度 | 有符号小端整数，单位为弧度 × 10,000,000 |
| 20 | 4 | 航空器纬度 | 有符号小端整数，单位为弧度 × 10,000,000 |
| 24 | 1 | 位置有效性标志 | 位字段 |
| 25 | 7 | 保留 | 作为不透明字节原样保留 |

坐标转换公式为：

```text
degrees = raw / 10,000,000 × 180 / pi
```

位置有效性标志如下：

| 位 | 名称 | 含义 |
| ---: | --- | --- |
| 0 | `aircraftPositionValid` | 置位时，经度和纬度有效 |
| 1 | `positionProducerMarker` | 观测到的生成端标记 |
| 2–7 | 保留 | 含义未定义；原样保留 |

位 0 置位时，经度必须位于 `[-180, 180]` 度范围内，纬度必须位于 `[-90, 90]` 度范围内。位 0 未置位时，无论存储的数值为何，两个坐标均不可用。

航空器标识符是第一个 NUL 之前的字节序列。仅接受非空 ASCII 字母数字标识符（`0`–`9`、`A`–`Z` 或 `a`–`z`）。无效标识符可以报告为不可用，而无需使整条报文无效。

## INFP 核心记录

INFP-10 和 INFP-11 使用相同形式的头部，但选择符、核心记录总长度、明文长度和密文长度不同。

### INFP-10 核心记录

INFP-10 核心记录的长度恰好为 128 字节：

| 偏移 | 大小 | 字段 | 编码或值 |
| ---: | ---: | --- | --- |
| 0 | 1 | 选择符 | `0x10` |
| 1 | 4 | 魔数 | ASCII `INFP` |
| 5 | 4 | `key_id` | 会话标识符 |
| 9 | 8 | `iv` | AES-CTR IV 前缀 |
| 17 | 2 | 明文长度 | 小端序 `109`（`0x006d`） |
| 19 | 109 | 密文 | 经 AES-128-CTR 加密的 INFP-10 明文 |

### INFP-11 核心记录

INFP-11 核心记录的长度恰好为 160 字节：

| 偏移 | 大小 | 字段 | 编码或值 |
| ---: | ---: | --- | --- |
| 0 | 1 | 选择符 | `0x11` |
| 1 | 4 | 魔数 | ASCII `INFP` |
| 5 | 4 | `key_id` | 会话标识符 |
| 9 | 8 | `iv` | AES-CTR IV 前缀 |
| 17 | 2 | 明文长度 | 小端序 `141`（`0x008d`） |
| 19 | 141 | 密文 | 经 AES-128-CTR 加密的 INFP-11 明文 |

### INFP-10 语义验证

完成结构验证和解密后，执行以下检查：

- 明文选择符为 `0x10`。
- 明文长度为 109 字节。
- 版本为 `2` 或 `3`。
- 每个可变文本长度不超过 20 字节。
- 航空器和应用端经度位于 `[-180, 180]` 度范围内。
- 航空器和应用端纬度位于 `[-90, 90]` 度范围内。
- 返航点坐标要么是不可用哨兵值对，要么是有效的经纬度值。
- 航向角位于 `[-180, 180]` 度范围内。
- GPS 时间、航空器经度和航空器纬度同时为零时，可以将该记录作为未初始化记录拒绝。
- 航空器标识符在作为有效文本提供时，必须是非空 ASCII 字母数字串。

当 JSON 实现无法精确保留更大的整数时，可以拒绝大于 `2^53 - 1` 的 GPS 毫秒值。

## INFP-11 明文

解密后的 INFP-11 明文长度恰好为 141 字节：

| 偏移 | 大小 | 字段 | 编码或值 |
| ---: | ---: | --- | --- |
| 0 | 1 | 选择符 | 必须为 `0x11` |
| 1 | 16 | 航空器标识符 | 以 NUL 终止或以 NUL 填充的 ASCII |
| 17 | 3 | 格式标记 | 必须为 `cc aa 03` |
| 20 | 1 | 用途长度 | 无符号；最大为 120 |
| 21 | 120 | 用途文本槽 | UTF-8；使用声明长度指定的前缀 |

标记的最后一个字节是版本值 `3`。

接受记录之前，必须验证选择符、精确的 141 字节长度、3 字节标记以及用途长度上限。航空器标识符采用与其他明文布局相同的验证规则。

## 接收方处理算法

以下伪代码给出完整的常规接收流程：

```text
sessions = map from 4-byte key_id to 16-byte K

for each input record:
    core = remove_and_validate_envelope(record)
    packet = parse_core(core)

    if packet is CRYP:
        require packet.length == 163
        require packet.magic == "CRYP"
        require packet.ciphertext_length == 32

        C1 = decode_affine_point(packet.C1_x, packet.C1_y)
        require C1 is a valid non-infinity SM2 point

        S = d * C1
        require S is not the point at infinity
        (x2, y2) = encode_affine_coordinates(S, 32-byte big-endian)

        t = SM3(x2 || y2 || 00000001)[0:16]
        K = packet.C2 XOR t

        require constant_time_equal(
            SM3(x2 || K || y2),
            packet.C3
        )
        require constant_time_equal(
            SHA-256(K)[0:4],
            packet.key_id
        )

        sessions[packet.key_id] = K
        counter = packet.iv || (0x00 * 8)
        auxiliary = AES-128-CTR(K, counter, packet.ciphertext)
        validate_and_parse_cryp_auxiliary(auxiliary)

    if packet is INFP:
        require packet.magic == "INFP"
        require sessions contains packet.key_id
        K = sessions[packet.key_id]

        counter = packet.iv || (0x00 * 8)
        plaintext = AES-128-CTR(K, counter, packet.ciphertext)

        require plaintext[0] == packet.selector
        if packet.selector == 0x10:
            validate_and_parse_infp10(plaintext)
        else if packet.selector == 0x11:
            validate_and_parse_infp11(plaintext)
        else:
            reject
```

## 验证失败

存在以下任一适用情况时，拒绝该记录：

- 选择符、魔数、核心长度或内部长度无法识别。
- 封装 CRC 错误；不得尝试隐式修复。
- `C1` 无效或不在曲线上；必须在标量乘法之前拒绝。
- CRYP 记录的 `C3` 或 `key_id` 验证失败。
- 不得保留或使用来自已拒绝 CRYP 记录的候选会话密钥。
- 如果没有与 INFP 记录的 `key_id` 完全匹配且已经过认证的密钥，不得解密该记录。
- 解密后的 INFP 数据中，选择符或结构常量与外层记录不一致。
- 保留字段和未知字段应视为不透明数据；转发或重新编码记录时必须原样保留。
